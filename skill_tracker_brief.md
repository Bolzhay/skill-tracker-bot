# Skill Tracker Bot — технический бриф

Telegram-бот для развития любых навыков через ансамбль ИИ-моделей.
Сейчас им пользуется владелец, но данные хранятся по пользователям — бота
можно открыть для других (см. "Доступ и пользователи").

## Идея в двух словах

Создаёшь "скилл" (например: пиксель-арт, шахматы, риторика).
Бот через ансамбль моделей строит продуманное дерево уровней под твой
стартовый уровень. По команде генерит задание. Ты присылаешь пруф
(фото/голосовое/видео/текст), ансамбль моделей его строго оценивает,
даёт фидбек и начисляет опыт. Со временем растёшь по уровням и рангам,
копится архив пруфов ("тогда vs сейчас").

## Запуск

```
pip install -r requirements.txt          # для разработки: requirements-dev.txt
python -m bot.main                       # polling, локально
python -m pytest                         # тесты (без сети и ключей)
```

Нужен `.env` (шаблон — `.env.example`): токен бота, путь к service account
Firebase, ключ OpenRouter, `CLAIM_CODE`. Первый запуск: владелец отправляет
боту `/claim <CLAIM_CODE>` — до этого бот закрыт для всех.

## Репозиторий и секреты

Репозиторий публичный. `.env` и ключ сервисного аккаунта Firebase перечислены
в `.gitignore` и в историю не попадали; перед публикацией вся история
проверена на токен бота, ключи OpenRouter, Google и YouTube, `CLAIM_CODE` и
приватный ключ Firebase. Если секрет всё же попадёт в коммит, его отзывают в
источнике (токен бота — в @BotFather, ключ Firebase — в консоли Firebase,
API-ключи — в кабинете провайдера): одного удаления из истории мало.

## Стек

- **Язык:** Python, **aiogram 3**
- **БД:** Firebase Firestore. Схема документ-ориентированная, всё
  пользовательское лежит под `users/{telegram_id}` (см. "Схема данных").
  Правила в консоли должны быть deny-all (`allow read, write: if false;`).
  Бот ходит через Admin SDK и правила обходит, поэтому открывать их
  ("test mode") не нужно и нельзя
- **Модели:** через OpenRouter, **только бесплатные (`:free`)** — осознанное
  ограничение проекта: ноль расходов. Пул: `nvidia/nemotron-3-ultra` (текст, самая надёжная),
  `google/gemma-4-31b` (vision; часто 429 от общей очереди Google AI Studio),
  `dots-studio/dots-3-note-preview` (текст и картинки, третий разработчик;
  preview-модель, может исчезнуть). Уроки: `thinkingmachines/inkling:free`
  не отвечает никому вне "agentic harness" (403) и убран;
  `inclusionai/ling-3.0-flash-vl` пропал из бесплатного списка OpenRouter
  (404 на любой вызов, замечено 2026-10-09) и заменён на dots; некоторые
  модели не поддерживают `response_format`, поэтому JSON просим в промпте
  и разбираем сами (включая ```-обёртки). 404 с пометкой "ZDR violation"
  означает, что в аккаунте OpenRouter включён Zero Data Retention: все
  бесплатные модели при нём недоступны (настройка в Settings → Privacy)
- **Второй провайдер (необязательный):** Gemini API от Google напрямую
  (OpenAI-совместимый; ключ из AI Studio; доступен не во всех странах).
  Запись модели с префиксом `google:` уходит туда и требует
  `GEMINI_API_KEY`; без ключа такие записи пропускаются. Зачем: у OpenRouter
  50 запросов в сутки на всё, а на бесплатном тарифе Google у каждой Gemma 4
  (26B и 31B) 30 запросов в минуту, 16 тыс. токенов в минуту и 14 400
  запросов в сутки (таблица AI Studio, 2026-10-09). Модели Gemini Flash на
  этом тарифе почти бесполезны (5–10 запросов в минуту, 20 в сутки) и не
  используются. Gemma от Google (`GEMMA` в `bot/llm/models.py`) стоит в
  каждой цепочке: первой там, где первой раньше была gemma, иначе после
  ведущей модели. Поэтому после исчерпания лимита OpenRouter бот продолжает
  работать на Google. Проверено вживую на одной Google (ключ OpenRouter
  намеренно сломан): дерево уровней (12 уровней) ~7 мин, задание ~50 с,
  оценка фото ~80 с — медленно из-за 31B с рассуждениями, но работает.
  Нюансы:
  - ключ нужен из проекта БЕЗ привязанного платёжного аккаунта (бесплатный
    тариф): у проекта с привязкой — Tier 1, и при нулевом балансе предоплаты
    все его ключи отвечают 402 даже для бесплатной gemma (проверено); вернуть
    проект на бесплатный тариф можно, отключив оплату в Cloud Console;
  - `.env` главнее переменных среды ОС (`load_dotenv(override=True)`): старый
    `GEMINI_API_KEY` в переменных ОС (например, оставшийся от другого
    инструмента) иначе подменял бы ключ из `.env`;
  - запросы к Google идут только по IPv4: в некоторых сетях IPv6-маршрут до
    Google не работает, и каждое подключение висело бы минутами;
  - gemma на этом эндпоинте отвечает с блоком `<thought>…</thought>` перед
    ответом — он вырезается перед разбором JSON; 31B отвечает за 30–50 с,
    26B-A4B за 5–6 с (в цепочках стоит 31B; быстрая 26B — возможное
    ускорение, качество не проверялось); обе понимают картинки;
  - NVIDIA (build.nvidia.com) рассматривалась и отпала: регистрация требует
    подтверждения телефона, а он принимается не из всех стран
- **Антиповтор:** локальное сравнение слов (cosine по 5-буквенным основам,
  без внешнего API) + проверка второй моделью. Настоящие эмбеддинги не
  используем: они платные, а смысловые дубли ловит LLM-проверка
- **Аудио/видео:** `faster-whisper` локально (модель `small`, CPU,
  бесплатно, аудио не уходит в облако). Расшифровывается звук;
  видеоряд не анализируется
- **Архив пруфов:** Firestore (байты ≤ 900 КБ в отдельном документе, у
  документа лимит 1 МиБ) + `file_id` Telegram как запасной указатель.
  Firebase Storage недоступен без платного тарифа
- **Хостинг:** пока локально (polling). Облако требует платёжного
  аккаунта — см. "Открытые вопросы"

## Доступ и пользователи

- **Whitelist** на уровне middleware: до активации бот отвечает только на
  `/claim`; после — только пользователям с `users/{id}.allowed = true`.
  Чужому бот показывает его Telegram ID, чтобы владелец мог добавить
- `/claim <код>` — владелец активирует бота один раз (код из `.env`);
  данные из старой односкилловой схемы (`skills` верхнего уровня)
  переносятся под владельца автоматически
- `/allow <id>`, `/deny <id>` — только владелец. У каждого пользователя
  свои скиллы, задания и архив

## Ключевые архитектурные принципы

### 1. Ничего не делает одна модель за один проход

И построение дерева, и генерация заданий, и оценка — везде работает
**ансамбль/цепочка моделей**. Это осознанный компромисс: дольше, зато
качественнее. Латентность не приоритет: пайплайн может работать минуты.

**Обработка сбоев (все пайплайны, `bot/llm/openrouter.py`):** на каждый
вызов — цепочка моделей. Каждая модель получает до 3 попыток с паузой
(5 с, 10 с), затем берётся следующая. Сбоем считается не только ошибка
HTTP, но и пустой ответ, битый JSON и валидный JSON не той формы
(пустой `{}`) — форму проверяет `validate` вызывающего. Постоянные отказы
(HTTP 400/401/402/403/404: неверный ключ, кончились кредиты, модель
недоступна) не повторяются —
сразу следующая модель, чтобы не тратить время и квоту. Если не сработало
ничего — бот честно пишет об этом в чат, а не зависает.

Исключение — исчерпан лимит самого OpenRouter (отличается от 429 от
перегруженного провайдера наличием заголовков `X-RateLimit-*` с нулём
остатка): ретраи и другие модели OpenRouter бесполезны, лимит общий на
аккаунт, поэтому они пропускаются. Записи `google:` этот лимит не
затрагивает, их пробуют дальше; если не ответил никто — бот пишет про
лимит. Это определено по документации, а не по живому ответу — вживую
лимит не выбивали, чтобы не сжечь квоту. 429 от Google считается обычным
"занято" (ретрай и следующая модель), даже если на деле кончилась дневная
квота: отличать одно от другого вживую пока не изучали.

### 2. Построение дерева уровней (при создании скилла)

1. Онбординг, FSM (`StatesGroup`): название, затем 3 вопроса — самооценка,
   что пробовал, цель. Вопросы зашиты в код. Скилл создаётся только после
   ответов (брошенный диалог ничего не оставляет); ответы сохраняются в
   скилле — они калибруют и дерево, и задания, и позволяют перестроить
   дерево кнопкой, если модели сбойнули
2. Модель А — черновик дерева (JSON: уровни, цель, критерии)
3. Модель Б — критика: пробелы, резкие скачки, шаблонность, а также
   несоответствие уровню человека (профессиональный жаргон)
4. Модель А — доработка с учётом критики (один раунд)
5. Модель-судья — итоговое дерево, запись в Firestore. Сложность и язык
   калибруются под реальную самооценку: без жаргона и без привязки к
   конкретному софту, который человек не упоминал

Строится в фоне (`asyncio.create_task`), бот при этом не блокируется.

### 3. Генератор заданий — ансамбль с защитой от однотипности

Только по команде/кнопке, без автоматического пуша. Повторный запрос,
пока предыдущее не закрыто, просто генерирует новое — старые остаются в
истории.

Пайплайн:
1. Модель предлагает задание под текущий уровень и самооценку ученика.
   **Одно задание = одна конкретная цель** (не свалка техник); к нему
   идёт краткая подсказка и тип пруфа
2. Быстрый локальный фильтр: сходство с последними 10 заданиями ≥ 0.5 →
   сразу переделка, без вызова модели
3. Иначе вторая модель проверяет смысловое сходство и неожиданность
4. Похоже → переделка со сменой "оси" (материал, контекст, ограничение,
   сочетание техник); до 3 переделок, потом берём последний вариант
5. Каждое 6-е задание — wildcard, нарочно ломающий паттерн

`/hint` — развёрнутая подсказка к открытому заданию: инструменты, шаги,
на что смотреть. У моделей нет живого поиска, а выдуманные ссылки вели бы
в никуда, поэтому модель лишь формулирует 1–3 **поисковых запроса** для
YouTube, а настоящие ролики находит сам бот через YouTube Data API
(`bot/youtube.py`): до 4 ссылок с названием и каналом. Каждый запрос —
один из 100 бесплатных поисков в сутки на проект (по документации
YouTube), то есть примерно 30–50 подсказок в день. Ключ
`YOUTUBE_API_KEY` берётся в Google Cloud (включить YouTube Data API v3,
создать ключ и ограничить его этим API), оплата не нужна; ключ уходит в
заголовок, а не в URL, чтобы не попадать в логи. Нет ключа, кончилась
квота или сбой сети — подсказка приходит без ссылок, со списком запросов
для ручного поиска. Проверено вживую 2026-10-09 (Gemma на Google + поиск).
К самим заданиям ссылки пока не прикрепляются.

### 4. Оценщик — строгий, с ролью "скептика"

ИИ склонен переоценивать из вежливости, поэтому строгость встроена в
процесс: два независимых vision-анализа фото (разные модели, параллельно),
затем модель-скептик ("ищи недочёты, не хвали без оснований") выносит
вердикт `{feedback, task_completed, issues, strengths}`.

- **Оценивается задание, а не весь уровень.** Задания намеренно узкие,
  поэтому ни одно не покрывает все критерии уровня; критерии даны оценщику
  только как контекст строгости
- **Пруфы:** фото (в т.ч. файлом — без сжатия, важно для пиксель-арта),
  голосовое, аудио, видео, текст. Аудио/видео → Whisper → расшифровка
  оценивается как текст (в промпте оговорено, что ошибки распознавания не
  должны снижать оценку). Показывается и сама расшифровка
- **Пересдача:** засчитанный пруф закрывает задание (`completed`); незасчитанный
  оставляет его открытым — следующее сообщение и есть пересдача, без команд.
  Если оценка не удалась из-за сбоя моделей, пруф не теряется — достаточно
  прислать снова. `/retry` заново открывает приём пруфа для последнего
  задания (и после перезапуска бота: FSM живёт в памяти)

**Отложено:** для задач с объективно верным решением (например, химия или
математика) генератор должен создавать эталонное решение, видимое только
оценщику. Вернуться, когда такой скилл понадобится.

### 5. Геймификация

- **Левелап:** уровень растёт после **3 засчитанных заданий** на этом
  уровне (`ATTEMPTS_TO_LEVEL_UP`). Не по XP. Зачёт
  старого задания не двигает новый уровень
- **XP:** засчитанная попытка — 10 + бонус за стрик (до +10), незасчитанная
  — 2 (участие)
- **Стрик:** по скиллу, по локальной дате (`TZ_OFFSET_HOURS`, по умолчанию
  UTC+5, потому что Telegram не отдаёт часовой пояс). Считается любая
  попытка; пропущенный день обнуляет серию
- **Ранги по XP:** Новичок → Ученик (50) → Упорный (150) → Практик (400)
  → Мастер (800) → Легенда (1500). Смена ранга объявляется
- **Бейджи:** первое засчитанное задание, 10 заданий, первый левелап,
  wildcard покорён, серия 3/7/30 дней. Выдаются один раз
- Правила — чистые функции в `bot/gamification.py`

### 6. Интерфейс

Постоянное меню (📋 Мои скиллы / ➕ Новый скилл) и inline-кнопки: карточка
скилла (задание, подсказка, пруф, история, "тогда vs сейчас"), кнопки под
заданием и под результатом. Если скилл один, команды работают без
названия; если несколько — предлагают выбрать кнопкой (или `/task название`).
`/cancel` выходит из любого диалога.

Команды: `/new_skill /task /hint /retry /history /progress /profile /cancel`,
владельцу ещё `/allow /deny`.

`/progress` — "тогда vs сейчас": первая и последняя засчитанные фото-работы
рядом + честный разбор прогресса от vision-модели. Нужно ≥ 2 засчитанных
фото-задания.

## Схема данных (Firestore)

```
meta/owner                                   {user_id}
users/{uid}                                  {allowed, role: owner|member, name}
users/{uid}/skills/{skillId}
  name, created_at, current_level_id, levels_total,
  xp_total, streak_count, streak_last_date (ISO), tasks_completed,
  badges [id], onboarding {self_assessment, experience, goal}
.../skills/{id}/levels/{levelId}
  order, title, criteria {summary, checks[]}, status (locked/active/done),
  successful_attempts
.../skills/{id}/tasks/{taskId}
  level_id, description, hint, media_type, is_wildcard, completed, created_at
.../tasks/{id}/attempts/{attemptId}
  media_type, ensemble_feedback {feedback, task_completed, issues, strengths},
  xp_awarded, created_at, has_blob,
  proof {kind, file_id, mime, size, text | transcript}
.../attempts/{id}/media/proof                {data (bytes ≤ 900 КБ), mime}
```

`tasks` лежат на уровне скилла (не внутри level), чтобы "последние N
заданий" был одним запросом без объединения между уровнями. Байты пруфа —
в отдельном документе, чтобы выборка попыток оставалась дешёвой.

## Тесты

`python -m pytest` — более 200 тестов без сети и ключей: чистая логика
(геймификация, антиповтор), слой данных на фейковом in-memory Firestore
(`tests/fake_firestore.py`), LLM-обёртка на `httpx.MockTransport`, пайплайны
на скриптованных ответах моделей, обработчики на заглушках Message, и
сквозные тесты через настоящий `Dispatcher` с фейковой сессией Telegram
(`tests/fake_telegram.py`) — они проверяют порядок роутеров, фильтры,
whitelist и FSM. Ключевая логика проверена мутациями (намеренная поломка →
тесты краснеют).
Вне pytest разово проверялись на настоящих сервисах: Firestore (лимит
документа, миграция) и расшифровка речи.

## Открытые вопросы

- **Лимит бесплатных запросов.** У OpenRouter на free-тире 50 запросов в
  сутки (и 20 в минуту) на весь аккаунт; один цикл "задание → пруф" тратит
  ~7–10 запросов (дерево уровней — от 4). С несколькими пользователями
  упрёмся быстро. Разовое пополнение баланса на $10 поднимает лимит до
  1000 в сутки (платно — пока не планируется). Бесплатный выход — gemma от
  Google (14 400 запросов в сутки на модель, см. "Стек"): когда OpenRouter
  исчерпан, бот работает на ней, только медленнее
- **Хостинг.** Нужен всегда включённый процесс; Cloud Run/Functions
  требуют привязанного платёжного аккаунта. Пока бот работает локально
  (polling), пока включён компьютер. Для деплоя понадобится webhook
- ~~Правила Firestore~~ — проверено: стоит deny-all
- **Видеоряд.** Для видео оценивается только звук; кадры не анализируются
- ~~Живые ссылки на материалы~~ — сделано для `/hint` (YouTube Data API);
  статьи и документация (не видео) потребовали бы другого поискового API
  (Tavily даёт 1000 запросов в месяц бесплатно, без карты)
- ~~Ретро-режим (еженедельная сводка)~~ — не зашло, не делать
